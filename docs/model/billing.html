Billing: visits to money

We build the invoices ourselves from visits. BillingMonth is the interface between the billing and maintenance modules: it turns delivery facts into billable items, groups them into invoices, and answers to ION only through the per-task reconcile. QuickBooks holds issued invoices and echoes line ids back.

The decision and what it deletes

Ruled Self-build. The old write-ahead promise, ION invoice matching, and expected-vs-actual gates existed only to audit ION's invoices — gone. The Reconciler survives with one job: sum the month's billable items by task and agree with ION's per-task invoice facts on labor pricing and consumable completeness. Our invoice grouping never enters that comparison.

Object model

aggregate root entity value object (dashed) domain service box = name | attributes | operations  ·  ◆— composition: the attribute holds the child OBJECTS  ·  - -→ reference: the attribute holds only an ID
The shape, in one paragraph BillingMonth (customer × month) is the aggregate root and the module boundary: billing's own representation of a month of delivered service. It OWNS the BillableItems (billing's translation of visits/usage — priced, claimable; source_id references delivery by id only) and OWNS the Invoices (1..N — normally one, splits allowed; each provably covering the month because the aggregate closes over all of them). IonInvoice is demoted to a value object: an immutable external fact {ion_task_id, number, amount} consumed by the Reconciler for the per-task check. ION doc numbers live only there; our invoices mint our own.
The billable item is the tracking backbone One row per billed thing: source_id (UNIQUE — exclusivity I-B1), task_id (the reconcile grain), invoice_id (grouping), qbo_line_id (QBO's echo at issue). "Where was this visit billed" is one indexed lookup; the visit itself carries only settled_at.

One invoice table: the mirror. Drafts are never stored. A draft invoice is a pure function of the month — items + grouping strategy — so it lives in memory and is rebuilt on demand, exactly like routes and the routing Optimal draft (derived state gets no table). The only durable invoice row is billing.invoices, the QBO mirror, written by the echo when issue() creates the real thing. The durable record of grouping is on the ITEMS: qbo_invoice_id + qbo_line_id, stamped at issue. task_billing_periods, billing_audit.maintenance_invoices, and maintenance_invoice_line_items all retire after phase 2.
Parents hold objects, never id lists BillingMonth has no invoice_ids attribute. In memory it holds the child OBJECTS (items[*], invoices[*] — the muted rows the diamonds anchor to). In storage the reference always lives on the CHILD as its FK (invoices.billing_month_id, billable_items.billing_month_id) — the repository finds children by querying that FK, never by reading a list off the parent. An id-array column on the parent would be a second copy of the same fact, guaranteed to drift. Cross-aggregate references are the id attribute on the REFERRING side, drawn as the dashed arrows.
How object references work in code Composition (filled diamond): the owner's attribute holds the child objects — month.items is an in-memory array of BillableItem instances, loaded and saved with the month as one unit. Reference (dashed arrow): the attribute holds ONLY the id as plain data — item.source_id is a string; turning it into a Visit is a separate act through a repository. Same storage either way (rows + FKs); the difference is what gets reconstituted into memory together.
