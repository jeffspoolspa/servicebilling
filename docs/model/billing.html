Billing: visits to money

We build the invoices ourselves from visits. BillingMonth is the interface between the billing and maintenance modules: it turns delivery facts into billable items, groups them into invoices, and answers to ION only through the per-task reconcile. QuickBooks holds issued invoices and echoes line ids back.

The decision and what it deletes

Ruled Self-build. The old write-ahead promise, ION invoice matching, and expected-vs-actual gates existed only to audit ION's invoices — gone. The Reconciler survives with one job: sum the month's billable items by task and agree with ION's per-task invoice facts on labor pricing and consumable completeness. Our invoice grouping never enters that comparison.

Object model

The shape, in one paragraph BillingMonth (customer × month) is the aggregate root and the module boundary: billing's own representation of a month of delivered service. It OWNS the BillableItems (billing's translation of visits/usage — priced, claimable; source_id references delivery by id only) and OWNS the Invoices (1..N — normally one, splits allowed; each provably covering the month because the aggregate closes over all of them). IonInvoice is demoted to a value object: an immutable external fact {ion_task_id, number, amount} consumed by the Reconciler for the per-task check. ION doc numbers live only there; our invoices mint our own.
The billable item is the tracking backbone One row per billed thing: source_id (UNIQUE — exclusivity I-B1), task_id (the reconcile grain), invoice_id (grouping), qbo_line_id (QBO's echo at issue). "Where was this visit billed" is one indexed lookup; the visit itself carries only settled_at.

Processing model — one loop, composed policies

Fallback: abstract Invoice (lines, lifecycle, payment fold, event recording) is extended by MaintenanceInvoice (built from a BillingMonth’s items) and ServiceInvoice (from a work order). Payment handling is NOT a subclass — it is a composed CollectionPolicy: AutopayCollection charges the stored PaymentMethod first (a decline HOLDS, the delivery becomes a receipt); ManualCollection delivers and waits. The processing loop calls invoice.collection.collect(…) — dynamic dispatch, no if-statements, no {kind} × {autopay} class explosion. Outlets (ports): DeliveryChannel (email/SMS plugs), PaymentGateway, IonLogEditor (the Variance edit path; Windmill script pending). Money objects are views of the existing QBO mirrors — no new tables.

Checks, the gate, and how an invoice gets made

The question this section settles: what tells the system a month is good to invoice — and the answer is nothing stamps a status. Checks write FACTS (findings). Readiness is a rule the aggregate evaluates over those facts, at the moment of issuing. Same discipline as everywhere else: derive, never stamp.

Legend. Teal 1.6px = aggregate root · blue = entity · grey dashed = value object · purple dashed = interface / domain service. Solid line with a filled diamond = composition (the month OWNS its items and findings; both cascade with it). Dashed open arrow = reference or dataflow across a boundary. Orange rows are proposed, not yet in code.

RULED · the signal mechanism A check never enqueues anything and never marks a month "ready". It writes findings. Readiness is derived — a month is issuable when it has items, has no BLOCKING open findings, and has not already been issued. The transition that enqueues downstream work is the issue itself (items gain qbo_invoice_id), never the check. This keeps three properties: re-running checks is free and side-effect-less, a stale "ready" flag cannot exist, and authorization stays with the human who dispositions the findings.

When it runs, and on what

checkMonth(customerId, month) is re-runnable at any time and has no side effect except replacing that month’s OPEN findings. It runs after every accrual — month-end sweep, a variance re-accrual, a reconcile-driven refresh, or a human pressing re-check in the workbench. Its whole input is MonthContext, assembled by the application layer so the rules stay pure: the month’s items, visits and terms, the customer (residential derived in its constructor), item profiles with typical quantities, the peer and self chem baselines, and what ION says about each task’s config.

The gate lives on the aggregate

BillingMonth.gate(findings) → GateVerdict. It is a domain rule about the month’s own readiness, so it belongs to the object that owns the items — not to a query, a view, or the UI. The verdict carries its blockers, so “why is this month not invoiced” is answerable without re-deriving anything.

InvariantRuleEnforced by
I-G1A month with no items is not issuable — there is nothing to billgate

WHY THE GATE IS RE-EVALUATED AT ISSUE TIME A month can be enqueued as ready and stop being ready before the worker claims it — a re-ingest lands new chemicals, someone reopens a finding. So issueMonth loads findings and calls the gate itself rather than trusting the queue row. This is the same claim-time-read rule the workflow architecture already applies to charging: the queue row is an envelope naming a unit, never a snapshot of its state.

RULED · checks never hand off directly Checks do not pass passing months to processing. Three reasons, each load-bearing: bill-review findings need a HUMAN between detection and money; coupling detection to processing would make a re-check a side-effectful act; and the workflow architecture requires authorization to happen BEFORE enqueue, because a queue row means “safe to process”.

One invoice table: the mirror. Drafts are never stored. A draft invoice is a pure function of the month — items + grouping strategy — so it lives in memory and is rebuilt on demand, exactly like routes and the routing Optimal draft (derived state gets no table). The only durable invoice row is billing.invoices, the QBO mirror, written by the echo when issue() creates the real thing. The durable record of grouping is on the ITEMS: qbo_invoice_id + qbo_line_id, stamped at issue. task_billing_periods, billing_audit.maintenance_invoices, and maintenance_invoice_line_items all retire after phase 2.
Parents hold objects, never id lists BillingMonth has no invoice_ids attribute. In memory it holds the child OBJECTS (items[*], invoices[*] — the muted rows the diamonds anchor to). In storage the reference always lives on the CHILD as its FK (invoices.billing_month_id, billable_items.billing_month_id) — the repository finds children by querying that FK, never by reading a list off the parent. An id-array column on the parent would be a second copy of the same fact, guaranteed to drift. Cross-aggregate references are the id attribute on the REFERRING side, drawn as the dashed arrows.
How object references work in code Composition (filled diamond): the owner's attribute holds the child objects — month.items is an in-memory array of BillableItem instances, loaded and saved with the month as one unit. Reference (dashed arrow): the attribute holds ONLY the id as plain data — item.source_id is a string; turning it into a Visit is a separate act through a repository. Same storage either way (rows + FKs); the difference is what gets reconstituted into memory together.
